Add the persistence tier's HTTP surface -- `servers/database_server.py` and the first HTTP store implementation, `HttpGuildAnalyticsStore` -- both inert, with nothing constructing them until the db pod entrypoint lands. This settles the retry question the extraction spec asked to answer before MR 2: the pod owns retrying the database because it is the layer nearest to it, so a store failure that has already exhausted `async_retry_database_commands` comes back as HTTP 200 with a typed error body rather than a 5xx. The client re-raises it as `DatabaseUnavailable` and does not retry. Encoding it as 5xx instead would put the client's 1+2+4 second ladder on top of the pod's, turning one `get_playlist` into nine attempts -- the same compounding shape as the 2026-08-26 incident. Non-2xx stays reserved for the pod itself being absent or draining, which is the one failure the bot side is nearest to and the only one worth retrying from there.
