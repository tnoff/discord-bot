- The `discord-db` pod can run `alembic upgrade head` at startup, behind `general.run_migrations` (default **false**). Nothing ran migrations before this: `setup_db` called `BASE.metadata.create_all`, which creates missing tables and never `ALTER`s, so every schema change to date was applied by hand. The runner goes before the engine and long before anything binds a port -- a process should not serve a schema it has not verified, and `alembic/env.py` calls `asyncio.run()` at module scope, so it cannot live inside the event loop. `setup_db` keeps its `create_all` call until the flag is on in prod, because with the flag off it is still the only thing that builds a schema.
- `alembic/env.py` takes a `pg_advisory_xact_lock` before running revisions. `discord-db` runs `replicas: 1`, but two pods exist on every rollout (`maxSurge: 1`) and a node loss mid-rollout can leave two of them starting -- and nothing enforces the replica count. Measured without the lock: the loser dies on `UniqueViolationError` against `pg_type_typname_nsp_index`, both processes having tried to create `alembic_version`. The database survives either way (postgres DDL is transactional); the pod does not. env.py also now prefers a DSN passed by the runner over `DATABASE_URL`, so the upgrade cannot land on a different database than the process serves.
- `Dockerfile.db` ships `alembic/` and `alembic.ini`, in `${WORKDIR}` rather than `${APPDIR}` -- the install layer ends with `rm -rf` on `${APPDIR}`, so anything landed there is deleted in the same layer.
- Two new guards, both of which fail on the real regression rather than a proxy for it: `alembic` joins the import-boundary vocabulary, so the CLI cannot reach another image through an import chain; and a Dockerfile check asserts that only `Dockerfile.db` COPYs the migrations. The second exists because that property broke once and nothing noticed -- the MR 4 cutover took the alembic CLI out of the bot and broker images while their COPY lines stayed, and it was found by hand weeks later.
- `tests/test_alembic_chain.py` gains the two behaviours this design rests on: concurrent upgrades both exit 0 with exactly one running revisions, and an older image refuses a database stamped at a revision it does not ship (`Can't locate revision`) rather than serving against a schema it cannot verify.
